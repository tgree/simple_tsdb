ACCESS CONTROL
==============
A simple_tsdb root can hold an access control list (ACL) that limits which
databases each user can reach over tsdbserver's SSL port, and what they can do
there.  The list lives in the "acl" file in the root, next to "passwd", and is
managed with tsdbcli2.

Who is restricted
-----------------
Only users who log in over the SSL port are restricted.  tsdbserver's plain
TCP port only listens on the loopback interface and has no users, so it can
still do anything, as can tsdbcli2 and tsdbreflector's local port.

Permissions
-----------
A user can hold any of these permissions on a database:

    read    LIST MEASUREMENTS, LIST SERIES, ACTIVE SERIES, COUNT, SELECT,
            SUM, INTEGRATE, COMPUTE and SUM COMPUTE, plus GET SCHEMA
    write   CREATE MEASUREMENT and WRITE POINTS, plus GET SCHEMA
    delete  DELETE POINTS
    all     read, write and delete

Permissions granted on "*" apply to every database, including databases that
don't exist yet, and add to whatever the user holds on a particular database.
CREATE DATABASE needs all permissions on "*".  NOP, GET VERSION and LIST
DATABASES are always allowed, but LIST DATABASES only lists the databases the
user holds some permission on.

Names match exactly.  A grant on "Sensors" doesn't cover "sensors", even on a
case-insensitive file system such as macOS's default APFS, where simple_tsdb
also refuses to open "Sensors" when the directory is really "sensors".

A command on a database that the user holds no suitable permission on fails
with PERMISSION_DENIED (-39), whether or not the database exists, so users
can't find out the names of databases they can't use.  tsdbserver logs each
refusal with the user, command and database.

Turning access control on
-------------------------
Roots created with "tsdbcli2 --init-root" start with access control on and
nothing granted, so authenticated users can't reach anything until they are
granted something.

Roots created before access control existed have no acl file, and every user
can still do anything there.  To turn access control on for such a root, run:

    enable acls

in tsdbcli2.  From then on, authenticated users can only do what they have
been granted, so grant each user what they need straight away.

Managing the list
-----------------
In tsdbcli2:

    grant <permissions> on <database|*> to <user>
    revoke <permissions> on <database|*> from <user>
    list grants
    list grants for <user>

<permissions> is a comma-separated list such as "read,write" or "all".  GRANT
adds to whatever the user already holds; the user must already exist, but the
database doesn't have to.  REVOKE removes permissions, and a user's entry for
a database disappears when nothing is left.  Revoking on "*" only changes the
user's "*" entry, not their entries for particular databases.  For example:

    add user alice <password>
    grant read on * to alice
    grant write,delete on alice_data to alice
    list grants

tsdbserver reads the acl file for every command, so changes take effect
immediately, even for connections that are already open.

The acl file
------------
After a comment line saying that it is generated by tsdbcli2, the file has
one line per user and database:

    alice *          read
    alice alice_data write,delete

tsdbcli2 rewrites it in this sorted form on every change, holding an exclusive
lock on passwd.lock and renaming a complete new file into place, so it
shouldn't be edited by hand.  If the file can't be parsed, tsdbserver refuses
every authenticated command that names a database with INVALID_ACL_FILE (-40)
until it is fixed, and tsdbcli2 reports the line number of the problem.

tsdbreflector
-------------
A reflector logs into the remote tsdbserver as its remote_user and writes to
the databases in its map lines.  It needs write permission on each of those
remote databases, which also lets it check their schemas:

    grant write on data_logger_xyz123_data to data_logger_xyz123

See REFLECTOR.txt.
